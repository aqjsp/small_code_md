# Git工作流

## 1 集中式工作流

### 1.1 什么是集中式工作流
集中式工作流是最简单的工作流，它使用一个中央仓库，所有开发者都从这个仓库克隆代码，并将更改推送回这个仓库。这种工作流类似于传统的SVN工作方式。

### 1.2 工作流程
1. 从中央仓库克隆代码
2. 在本地进行开发和提交
3. 将更改推送到中央仓库

### 1.3 实施步骤
```bash
# 1. 克隆中央仓库
git clone https://github.com/team/project.git
cd project

# 2. 创建功能分支（可选）
git checkout -b feature-xyz

# 3. 进行开发和提交
git add .
git commit -m "Add feature XYZ"

# 4. 推送到中央仓库
git push origin main  # 或者 git push origin feature-xyz
```

### 1.4 优点
- 简单易学，适合小型团队
- 没有复杂的分支管理
- 与SVN等集中式版本控制系统类似

### 1.5 缺点
- 容易产生冲突
- 不适合大型项目或团队
- 功能开发与主分支混合

## 2 功能分支工作流

### 2.1 什么是功能分支工作流
功能分支工作流是在集中式工作流的基础上，为每个新功能或修复创建独立的分支。这样可以隔离功能开发，不影响主分支的稳定性。

### 2.2 工作流程
1. 从主分支创建功能分支
2. 在功能分支上进行开发和提交
3. 将功能分支合并回主分支

### 2.3 实施步骤
```bash
# 1. 克隆仓库并切换到主分支
git clone https://github.com/team/project.git
cd project
git checkout main

# 2. 确保本地主分支是最新的
git pull origin main

# 3. 创建并切换到功能分支
git checkout -b feature-user-authentication

# 4. 在功能分支上进行开发和提交
git add .
git commit -m "Add user authentication logic"

# 5. 推送功能分支到远程仓库
git push origin feature-user-authentication

# 6. 创建Pull Request或Merge Request
# 7. 代码审查和合并
# 8. 合并后删除功能分支
git branch -d feature-user-authentication
git push origin --delete feature-user-authentication
```

### 分支命名规范
```bash
# 功能分支
feature/user-authentication
feature/payment-gateway

# 修复分支
fix/login-bug
fix/memory-leak

# 发布分支
release/v1.2.0
release/2023-12-01

# 热修复分支
hotfix/critical-security-patch
hotfix/production-bug
```

### 2.4 优点
- 功能开发隔离，不影响主分支
- 便于代码审查和协作
- 可以并行开发多个功能
- 更好的项目组织和管理

### 2.5 缺点
- 需要良好的分支管理
- 可能产生大量分支
- 需要定期合并主分支的更新

## 3 Git Flow工作流

### 3.1 什么是Git Flow
Git Flow是由Vincent Driessen提出的一个严格的分支模型，它定义了围绕项目发布的严格分支模型，为不同阶段的开发提供了清晰的指导。

### 分支类型
1. **主分支（main/master）**：稳定的生产代码
2. **开发分支（develop）**：最新的开发代码
3. **功能分支（feature/*）**：新功能开发
4. **发布分支（release/*）**：发布准备
5. **热修复分支（hotfix/*）**：紧急修复

### 4.2 工作流程
### 3.2 分支类型
1. **主分支（main/master）**：稳定的生产代码
2. **开发分支（develop）**：最新的开发代码
3. **功能分支（feature/*）**：新功能开发
4. **发布分支（release/*）**：发布准备
5. **热修复分支（hotfix/*）**：紧急修复

### 3.3 工作流程
```bash
# 1. 克隆仓库
git clone https://github.com/team/project.git
cd project

# 2. 创建开发分支（如果不存在）
git checkout -b develop origin/develop

# 3. 从develop分支创建功能分支
git checkout -b feature/user-authentication develop

# 4. 在功能分支上开发
git add .
git commit -m "Add user authentication logic"

# 5. 将功能分支合并回develop分支
git checkout develop
git merge --no-ff feature/user-authentication
git push origin develop
git branch -d feature/user-authentication

# 6. 从develop分支创建发布分支
git checkout -b release/v1.2.0 develop

# 7. 在发布分支上进行修复和测试
git commit -m "Fix bug in release"

# 8. 将发布分支合并到main和develop分支
git checkout main
git merge --no-ff release/v1.2.0
git tag -a v1.2.0 -m "Release version 1.2.0"
git checkout develop
git merge --no-ff release/v1.2.0
git branch -d release/v1.2.0

# 9. 创建热修复分支
git checkout -b hotfix/critical-bug main

# 10. 修复后合并到main和develop分支
git checkout main
git merge --no-ff hotfix/critical-bug
git tag -a v1.2.1 -m "Release version 1.2.1"
git checkout develop
git merge --no-ff hotfix/critical-bug
git branch -d hotfix/critical-bug
```

### 3.4 Git Flow工具
```bash
# 安装git-flow
# macOS
brew install git-flow-avh

# Ubuntu/Debian
apt-get install git-flow

# 使用git-flow
git flow init
git flow feature start user-authentication
git flow feature finish user-authentication
git flow release start v1.2.0
git flow release finish v1.2.0
git flow hotfix start critical-bug
git flow hotfix finish critical-bug
```

### 3.5 优点
- 严格的分支管理，适合大型项目
- 清晰的发布流程
- 支持并行开发和发布
- 便于版本管理和回滚

### 3.6 缺点
- 流程复杂，学习曲线陡峭
- 对于小型项目可能过于复杂
- 频繁的分支切换和合并

## 4 GitHub Flow工作流

### 4.1 什么是GitHub Flow
GitHub Flow是GitHub使用的一个简单的工作流，它基于功能分支工作流，但更加简化。它假设持续部署是可能的，并且主分支始终是可部署的。

### 4.2 工作流程
1. 从主分支创建功能分支
2. 在功能分支上进行开发和提交
3. 推送功能分支到远程仓库
4. 创建Pull Request
5. 代码审查和讨论
6. 合并到主分支
7. 立即部署

### 4.3 实施步骤
```bash
# 1. 克隆仓库
git clone https://github.com/team/project.git
cd project

# 2. 确保主分支是最新的
git checkout main
git pull origin main

# 3. 创建功能分支
git checkout -b feature-user-authentication

# 4. 进行开发和提交
git add .
git commit -m "Add user authentication logic"

# 5. 推送功能分支
git push origin feature-user-authentication

# 6. 在GitHub上创建Pull Request
# 7. 代码审查和讨论
# 8. 合并到主分支（通过GitHub界面或命令行）
git checkout main
git pull origin main
git branch -d feature-user-authentication
git push origin --delete feature-user-authentication
```

### 4.4 优点
- 简单明了，易于理解和实施
- 适合持续部署环境
- 强调代码审查和协作
- 减少分支管理的复杂性

### 4.5 缺点
- 假设主分支始终是可部署的
- 不适合需要长期发布周期的项目
- 缺乏明确的发布分支管理

## 5 GitLab Flow工作流

### 5.1 什么是GitLab Flow
GitLab Flow是GitFlow和GitHub Flow的结合体，它提供了更大的灵活性，允许团队根据项目需求选择合适的工作流。

### 5.2 工作流程
GitLab Flow有两种主要变体：
1. **环境分支**：为每个环境（如staging、production）创建分支
2. **发布分支**：为每个版本创建发布分支

### 5.3 环境分支工作流
```bash
# 1. 克隆仓库
git clone https://gitlab.com/team/project.git
cd project

# 2. 创建功能分支
git checkout -b feature-user-authentication main

# 3. 开发和提交
git add .
git commit -m "Add user authentication logic"

# 4. 推送功能分支
git push origin feature-user-authentication

# 5. 创建Merge Request到main分支
# 6. 代码审查和合并到main分支

# 7. 将main分支合并到staging分支
git checkout staging
git merge main
git push origin staging

# 8. 测试后，将staging分支合并到production分支
git checkout production
git merge staging
git push origin production
```

### 5.4 发布分支工作流
```bash
# 1. 克隆仓库
git clone https://gitlab.com/team/project.git
cd project

# 2. 创建功能分支
git checkout -b feature-user-authentication main

# 3. 开发和提交
git add .
git commit -m "Add user authentication logic"

# 4. 推送功能分支
git push origin feature-user-authentication

# 5. 创建Merge Request到main分支
# 6. 代码审查和合并到main分支

# 7. 创建发布分支
git checkout -b release-v1.2.0 main

# 8. 将发布分支合并到production分支
git checkout production
git merge release-v1.2.0
git push origin production

# 9. 标记发布
git tag -a v1.2.0 -m "Release version 1.2.0"
git push origin v1.2.0
```

### 5.5 优点
- 灵活性高，适应不同项目需求
- 结合了GitFlow和GitHub Flow的优点
- 支持环境分支和发布分支
- 适合持续部署和传统发布周期

### 5.6 缺点
- 需要根据项目需求选择合适的工作流
- 可能需要额外的分支管理
- 不如GitFlow或GitHub Flow那样标准化

## 6 选择适合的工作流

### 6.1 项目规模考虑
1. **小型项目/团队（1-5人）**：
   - 功能分支工作流
   - GitHub Flow

2. **中型项目/团队（5-20人）**：
   - 功能分支工作流
   - GitLab Flow

3. **大型项目/团队（20人以上）**：
   - Git Flow
   - GitLab Flow

### 6.2 发布周期考虑
1. **持续部署**：
   - GitHub Flow
   - GitLab Flow（环境分支）

2. **定期发布（每周/每月）**：
   - 功能分支工作流
   - GitLab Flow（发布分支）

3. **长期发布周期（季度/年）**：
   - Git Flow
   - GitLab Flow（发布分支）

### 6.3 团队经验考虑
1. **初学者团队**：
   - 功能分支工作流
   - GitHub Flow

2. **有经验团队**：
   - Git Flow
   - GitLab Flow

### 6.4 项目复杂度考虑
1. **简单项目**：
   - 功能分支工作流
   - GitHub Flow

2. **复杂项目**：
   - Git Flow
   - GitLab Flow

## 7 工作流最佳实践

### 7.1 分支管理
1. **保持主分支稳定**：
   ```bash
   # 定期合并主分支更新到功能分支
   git checkout feature-branch
   git merge main
   ```

2. **定期清理分支**：
   ```bash
   # 删除已合并的本地分支
   git branch -d feature-branch
   
   # 删除已合并的远程分支
   git push origin --delete feature-branch
   ```

3. **使用描述性分支名**：
   ```bash
   # 好的分支名
   feature/user-authentication
   fix/login-page-bug
   release/v1.2.0
   hotfix/security-patch
   
   # 避免的分支名
   feature1
   fix
   temp
   ```

### 7.2 提交管理
1. **编写清晰的提交信息**：
   ```bash
   # 好的提交信息
   git commit -m "feat(auth): Add user authentication with JWT tokens"
   
   # 避免的提交信息
   git commit -m "fix bug"
   git commit -m "update"
   ```

2. **原子提交**：
   ```bash
   # 每个提交只做一件事
   git add auth.js
   git commit -m "Add authentication logic"
   
   git add auth.css
   git commit -m "Style authentication form"
   ```

3. **定期提交**：
   ```bash
   # 定期提交，避免大量未提交的更改
   git add .
   git commit -m "Work in progress: partial implementation"
   ```

### 7.3 代码审查
1. **使用Pull Request/Merge Request**：
   - 确保代码质量
   - 促进知识共享
   - 发现潜在问题

2. **自动化检查**：
   ```bash
   # .git/hooks/pre-commit
   #!/bin/sh
   npm run lint
   npm test
   ```

3. **审查检查清单**：
   - 代码是否符合项目规范
   - 是否有适当的测试
   - 是否有安全漏洞
   - 是否有性能问题

### 7.4 持续集成
1. **自动化构建和测试**：
   - 每次提交触发构建
   - 自动运行测试套件
   - 自动化代码质量检查

2. **自动化部署**：
   - 测试环境自动部署
   - 生产环境手动触发部署

### 7.5 团队协作
1. **明确的工作流文档**：
   - 创建团队工作流指南
   - 定期更新和培训

2. **定期同步**：
   - 每日站会
   - 定期代码审查会议
   - 定期回顾和改进

3. **工具支持**：
   - 使用适当的Git托管平台
   - 配置适当的CI/CD工具
   - 使用适当的沟通工具

## 8 实用技巧

### 8.1 使用Git别名简化工作流
```bash
# 设置常用别名
git config --global alias.co checkout
git config --global alias.br branch
git config --global alias.ci commit
git config --global alias.st status
git config --global alias.unstage 'reset HEAD --'
git config --global alias.last 'log -1 HEAD'
git config --global alias.graph 'log --oneline --graph --decorate --all'

# 工作流相关别名
git config --global alias.feature '!f() { git checkout -b feature/$1; }; f'
git config --global alias.hotfix '!h() { git checkout -b hotfix/$1; }; h'
git config --global alias.release '!r() { git checkout -b release/$1; }; r'
git config --global alias.merge-feature '!mf() { git checkout main && git merge --no-ff feature/$1 && git branch -d feature/$1; }; mf'
```

### 8.4 自动化工作流脚本
```bash
#!/bin/bash
# start-feature.sh - 开始新功能开发的脚本

FEATURE_NAME=$1
if [ -z "$FEATURE_NAME" ]; then
  echo "Usage: ./start-feature.sh <feature-name>"
  exit 1
fi

# 确保在主分支上且是最新的
git checkout main
git pull origin main

# 创建功能分支
git checkout -b "feature/$FEATURE_NAME"

echo "Created feature branch: feature/$FEATURE_NAME"

```

```bash
#!/bin/bash
# finish-feature.sh - 完成功能开发的脚本

FEATURE_NAME=$1
if [ -z "$FEATURE_NAME" ]; then
  echo "Usage: ./finish-feature.sh <feature-name>"
  exit 1
fi

# 确保在功能分支上
CURRENT_BRANCH=$(git branch --show-current)
if [ "$CURRENT_BRANCH" != "feature/$FEATURE_NAME" ]; then
  echo "Error: You are not on the feature/$FEATURE_NAME branch"
  exit 1
fi

# 推送功能分支
git push origin "feature/$FEATURE_NAME"

echo "Pushed feature branch: feature/$FEATURE_NAME"
echo "Create a pull request on your Git hosting platform"
```

### 8.5 使用Git钩子增强工作流
```bash
# .git/hooks/pre-commit - 提交前检查
#!/bin/bash

# 运行代码格式检查
npm run format:check

# 运行代码质量检查
npm run lint

# 运行测试
npm test

# 检查提交信息格式
commit_regex='^(feat|fix|docs|style|refactor|test|chore)(\(.+\))?: .{1,50}'
if ! grep -qE "$commit_regex" .git/COMMIT_EDITMSG; then
    echo "Invalid commit message format"
    echo "Expected format: type(scope): subject"
    exit 1
fi
```

```bash
# .git/hooks/post-checkout - 切换分支后操作
#!/bin/bash

# 检查是否切换了分支
prev_head=$1
new_head=$2
branch_checkout=$3

if [ $branch_checkout = "1" ]; then
    # 安装/更新依赖（如果package.json变化）
    if git diff --name-only $prev_head $new_head | grep -q "package.json"; then
        echo "package.json changed, running npm install..."
        npm install
    fi
    
    # 显示分支信息
    echo "Switched to branch: $(git branch --show-current)"
    echo "Last 3 commits on this branch:"
    git log --oneline -3
fi
```

## 9 工作流故障排除

### 9.1 常见问题及解决方案
```bash
# 问题1: 合并冲突
# 解决方案:
git checkout main
git pull origin main
git checkout feature-branch
git merge main
# 手动解决冲突后
git add .
git commit -m "Resolve merge conflicts"

# 问题2: 推送被拒绝
# 解决方案:
git pull --rebase origin main
git push origin main

# 问题3: 误提交到错误分支
# 解决方案:
git checkout correct-branch
git cherry-pick wrong-branch-commit-hash
git checkout wrong-branch
git reset --hard HEAD~1
```

### 9.2 紧急情况处理
```bash
# 紧急热修复流程
git checkout main
git pull origin main
git checkout -b hotfix/critical-bug
# 修复问题
git add .
git commit -m "fix: Critical security vulnerability"
git checkout main
git merge --no-ff hotfix/critical-bug
git tag -a v1.2.1 -m "Hotfix version 1.2.1"
git push origin main --tags
git branch -d hotfix/critical-bug
git push origin --delete hotfix/critical-bug
```
